# Keep Android and Windows downloads together

The installed Android and Windows apps contain a copy of the web build. A Vercel
deployment cannot replace that installed copy. A shared passcode or web change
needs a fresh APK and Windows installer; users then install the new downloads.
There is no automatic installer/updater added by this change.

## One release command

Use a full-history checkout of current main on Windows. Keep the existing root,
Android and desktop npm dependencies installed. Set `JAVA_HOME` to the existing
JDK and `ANDROID_HOME` to the existing Android SDK, as described in the
[Android guide](../android-app/README.md). Do not install a missing JDK/SDK as a
side effect of building. Install the pinned Electron runtime with the existing
desktop setup command if it is not already present.

```powershell
npm run apps:test
npm run apps:build
```

`apps:build` always typechecks and creates a fresh production web build, then
syncs, verifies and packages both apps. It does not reuse an old `dist/` or an
old synced directory. This is the sample-data alpha release path: it ignores
ambient `VITE_*` settings and project `.env` files, explicitly selects sample
mode, and obtains the passcode from **`src/lib/demoAdminPasscode.ts`**. The
ordinary website build keeps its existing configuration behavior, including
explicit `VITE_ADMIN_PASSCODE` overrides. Changing only an override on Vercel
does not change the shared source used by these downloads.

Both package manifests, their lockfile metadata and Android's version settings
are updated together to `0.2.0-alpha.N`, with Android version code `N`, where
`N` is the full checkout's commit count. Do not use shallow history or build an
older revision to publish over a newer release; lowering Android's version
code is refused. Rebuilding the same commit reuses its version. Commit the
updated native metadata when preparing a release PR. No dependency versions
are changed by this versioning step.

The command runs Android debug assembly, lint and instrumentation-test APK
assembly. It verifies all root web files in both wrappers, allowing only the
two empty compatibility scripts generated by this Capacitor version. Windows
package checks verify the installed resources and secure wrapper boundary.
The real packaged Windows app must reject the old passcode and accept the
current shared passcode. Extracted APK assets receive the same login check in
real Chromium using the existing desktop Electron runtime. No reports are
submitted or approved by these tests. Android hardware/WebView checks still
need a phone and are not established by this browser check.

The outputs are:

- `android-app/android/app/build/outputs/apk/debug/app-debug.apk`
- `desktop-app/release/RTP-0.2.0-alpha.N-windows-x64-setup.exe`
- `.cache/native-apps/build-all.json`: source commit, version, web inventory
  hash, artifact sizes and SHA-256 hashes; it does not contain the passcode.

These outputs are ignored by Git. A zero-length or greater-than-100-MiB file
fails the release command because the connected Drive upload action currently
limits individual files to 100 MiB. The Windows full installer uses maximum
compression, English/Filipino Electron locale packs, and no differential-update
archive. Existing web fonts, movies, maps and other web resources are retained.

## Keep the shared Drive folder current

Publish **both verified outputs** into the existing
[RTP folder](https://drive.google.com/drive/folders/1mpUalyCgYrDXoN8L1KP7WVv11_p-VFSJ),
as `RTP.apk` and `RTP windows x64 setup.exe`. Preserve the folder and its public
read sharing because the landing QR points there. Prefer replacing each
existing file's bytes in place after grounding its ID, so its link remains
stable and old duplicate downloads do not accumulate. Do not delete unrelated
files. Read back the completed uploads, names, sizes and parent folder.

A shared passcode change is not a completed download release until **both**
apps are rebuilt and both uploads are verified. The build command does not
run a background watcher, upload files, change GitHub/Vercel settings or modify
already-installed copies. The connected Drive uploader remains a separate
authorized publishing step. An unattended CI publisher would need deliberately
configured Drive access and the existing Android signing identity; it must not
silently generate a new key for each build.

Keep Android's existing application ID and certificate so users can update
over their previous APK. The Windows app remains an unsigned testing alpha;
existing publisher/SmartScreen limitations still apply. See
[Android update requirements](https://developer.android.com/google/play/app-updates)
and the [desktop verification limits](../desktop-app/README.md#validation-recorded-on-2026-10-13).
